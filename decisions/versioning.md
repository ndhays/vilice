# Versioning and releases

**Decided 2026-06-09.** Records the release policy for the signed `steward` binary —
the *why* behind the flow already encoded in `install.sh`, `steward/Makefile`
(`sign`/`release`), and the `release/published/` tree.

## The one inviolable rule: a version is one set of bytes, forever

`install.sh <version>` pins a version and verifies its ed25519 signature before
installing the binary **as root**. That trust only holds if a version number maps to
exactly one signed artifact, permanently. **Never republish different bytes under an
existing version number** — not for a fix, not for a rebuild. A new artifact gets a new
version. Everything below follows from this.

## When to release

A release is a ceremony, not a commit. Cut one at a deliberate milestone — when the
blueprint's promises are true and `make test` is green:

1. bump `VERSION`, 2. `make release` (builds every arch in `ARCHES` — linux/amd64 and
linux/arm64 — signs **each tarball separately**, self-verifies, copies to
`release/published/`), 3. commit, 4. tag.

One signature per artifact, never one covering several: a signature has to name exactly
the bytes it vouches for. `install.sh` picks the arch from `uname -m` and refuses an
arch it has no build for, rather than defaulting to one and installing a binary that
cannot execute.

- **Pre-1.0:** `0.MINOR.PATCHbeta` milestones. Betas are disposable checkpoints, not
  contracts.
- **1.0** when the on-box contract is stable: the settled command set, the auth/scope
  model, and the record format. After 1.0 those are promises.
- **Patch** = fixes and security only; **minor** = new capability. No per-commit releases —
  a release produces a root-installable signed binary and deserves the ceremony.

## What to keep — two stores, not one

Conflating these is the trap.

- **The install host** (`releases/`, what `install.sh` fetches) is an **immutable
  archive.** Keep every *stable* version anything might still reference; the whole value
  of a pinned, signature-verified install is that an old URL keeps resolving to the same
  bytes. Never prune stable for space.
- **The local `release/published/` tree** is a **working set, not the archive** — and it
  is **not in git** (`.gitignore`), because binaries in git bloat history forever. It is
  regenerated by `make release` and holds whatever you have built locally: current stable
  plus current beta. Prune superseded *betas* freely; they are checkpoints, not contracts.

A consequence worth naming: **the signed artifacts exist only where someone ran
`make release`.** The site build copies that tree into `dist/releases/`, so *deploying
the site is what publishes a version* — and the `check-release.js` prebuild guard refuses
to build a site whose install page advertises a `VERSION` the tree doesn't have. That
guard is the thing that catches "the docs say 0.1.5beta and the host 404s."

Post-1.0, the served host should become the real archive (CI / object storage) with the
build no longer depending on one laptop's `dist/`. Until then the working set stays local
and deliberately small.

## Security updates: fix forward, yank with a record

- **Never overwrite.** A vulnerable artifact is fixed by shipping a *new* patched version,
  never by replacing bytes under the old number.
- **Betas: just delete** a bad one — not a contract, nothing owed.
- **Stable with a real vuln: yank, don't silently delete.** Pull it from the *install
  path* so `install.sh <bad>` can't fetch a known-vulnerable root binary — but leave a
  recorded marker (a `YANKED` note beside the version + a `SECURITY.md` advisory) of what
  existed and why it went. A vanished artifact with no record is its own integrity smell;
  the record is what keeps a removal honest (invariant 2, applied to releases).

## Roads not taken

- **A `latest` endpoint / floating tag.** `install.sh` takes an explicit version on
  purpose — a root install should name exactly what it trusts, not chase a moving target.
- **Keeping every beta in git as an archive.** Betas are checkpoints; the host (post-1.0)
  is the archive. Hoarding betas in git history buys nothing and costs repo weight.
